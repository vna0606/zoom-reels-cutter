# Zoom Reels Cutter (Reel Factory): технический обзор

Локальный инструмент для создания вертикальных Reels в двух режимах работы:

- **Подкаст** — прежний сценарий без изменений: пакетное преобразование готовых отрывков и поиск лучших моментов в длинном видео или YouTube-выпуске;
- **Эфир** — поиск ключевых моментов в горизонтальной записи Zoom, вебинара или онлайн-эфира, полноэкранная motion-презентация по смыслу фрагмента и один или два спикера в постоянных слотах снизу. Для рендера можно выбрать скорость 1.00–1.25× и визуальный пресет Editorial Lime или ITBooster.


> Установка и быстрый старт — в [README.md](../README.md). Здесь — технические детали пайплайна.

## ИИ-провайдер: Claude или Codex

Для поиска моментов и motion-плана эфира нужен авторизованный **Claude CLI** (`claude auth login`) **или Codex CLI** (`codex login`). Тихого перехода на эвристику нет: если выбранный ИИ недоступен, задача завершается понятной ошибкой (встроенный анализ работает только если выбран явно).

Выбор провайдера, по убыванию приоритета:

1. **Интерфейс** — список «ИИ: Авто / Claude / Codex» в настройках проекта (оба режима). Подсказка под списком показывает, кто готов; в карточках отрывков видно, какой ИИ использован.
2. **Переменные окружения** — `REEL_LLM_PROVIDER=auto|claude|codex`, `REEL_CLAUDE_MODEL` (по умолчанию `opus`; эти переменные можно также записать в файл `.env`), `REEL_CODEX_MODEL` (по умолчанию — модель Codex по умолчанию).
3. **Файл `reel_factory.config.json`** рядом с `app.py` (образец — `reel_factory.config.example.json`): `{"provider": "auto", "claude_model": "opus", "codex_model": null}`.

В режиме «Авто» берётся провайдер из окружения/конфига, если он готов, иначе первый готовый: Claude, затем Codex. Статус провайдеров: `GET /api/providers`.

## Режим «Подкаст»

Выберите «Подкаст» в верхнем переключателе. В этом режиме доступны оба прежних раздела — «Пачка видео» и «Умные нарезки», а обработка и формат результата остаются такими же, как раньше.

### Раздел «Пачка видео»

1. Перетащите в окно до 30 горизонтальных видео.
2. Выберите язык, качество распознавания и стиль субтитров.
3. Нажмите «Запустить обработку».
4. Следите за прогрессом каждого файла.
5. Скачайте готовые MP4 отдельно или одним ZIP-архивом.

Активное задание можно поставить на паузу и продолжить той же кнопкой. Пауза применяется на ближайшей контрольной точке обработки; загрузка, анализ кадров и кодирование останавливаются сразу на следующем обновлении прогресса.

### Раздел «Умные нарезки»

1. В режиме «Подкаст» выберите «Умные нарезки» в переключателе сценария.
2. Загрузите одно длинное видео либо вставьте публичную ссылку YouTube.
3. Выберите язык субтитров YouTube и допустимую длительность отрывков. Русский выбран по умолчанию.
4. Запустите анализ. И для загруженного файла, и для YouTube речь всегда распознаётся локально с пословными таймкодами (субтитры YouTube не используются: их пословное время синтетическое, а склейка кусков требует настоящих границ слов).
5. Редактор соберёт все ролики, в которых мысль цельная (по умолчанию без ограничения числа; поле «Сколько роликов собрать» = 0). Отметьте подходящие карточки и нажмите «Сделать вертикальные».
6. Скачайте готовые MP4 отдельно или одним ZIP-архивом.

YouTube-видео загружается только в HD: выбирается отдельная видеодорожка 720p–1080p и объединяется с лучшей аудиодорожкой. Если у ролика нет HD-варианта, загрузка завершается понятной ошибкой вместо использования 360p.

По умолчанию ИИ выбирается автоматически: авторизованный Claude CLI, затем Codex CLI. Встроенный эвристический режим без внешнего ИИ включается только явным выбором. Чтобы подключить Codex, один раз выполните `codex login`; для Claude — `claude auth login`.

## Режим «Эфир»

Этот режим рассчитан на горизонтальную локальную запись Zoom, вебинара или эфира, где одновременно видны демонстрация экрана и участники. Ссылка YouTube для режима «Эфир» не используется.

1. Выберите «Эфир» в верхнем переключателе.
2. Загрузите одну горизонтальную запись с компьютера.
3. Укажите язык речи, качество распознавания и допустимую длительность отрывков.
4. Запустите анализ. Транскрипция используется для поиска законченных тезисов, объяснений, демонстраций, инструкций и выводов; технические паузы, проверка связи и организационные реплики по возможности исключаются.
5. Отметьте подходящие карточки и нажмите «Сделать вертикальные».
6. Скачайте готовые MP4 отдельно или одним ZIP-архивом.

Распознавание в режиме «Эфир» тоже пословное (то же, что и в «Подкасте»): ролики собираются смысловым монтажом из всей записи (см. ниже), а субтитры берутся из той же транскрипции, пересчитанной на время готового ролика.

Во время обработки карточка проекта показывает текущий этап, обработанное и общее время записи и, когда данных достаточно, примерное оставшееся время. Если поиск моментов у ИИ-провайдера завершился ошибкой после сохранения транскрипции, кнопка повторного анализа использует уже загруженное видео и готовую транскрипцию: повторно распознавать многочасовой эфир не требуется.

Для каждого выбранного фрагмента Claude или Codex (по выбору) строит строгий визуальный план по локальной транскрипции: тезисы, подтверждённые числа, сравнения, этапы и схемы распределяются по всей временной шкале клипа. Если ИИ-провайдер недоступен или вернул некорректный план, рендер останавливается с понятной ошибкой — механическая подмена визуала отключена. План сохраняется вместе с fingerprint и повторно используется, пока не изменились транскрипция, длительность, пресет или данные карточки момента.

Локальный HyperFrames 0.8.4 превращает этот план в непрозрачный motion-фон 1080×1920 в выбранном пресете Editorial Lime или ITBooster. Поверх него накладываются один или два спикера: основной всегда находится слева снизу, второй — справа снизу, и смена активного голоса не меняет их местами. Субтитры остаются в безопасной нижней зоне. Звук всегда берётся из исходной Zoom-записи, motion-слой создаётся без аудио. Сам рендер HyperFrames работает локально с закреплённой версией CLI и локальным GSAP-файлом, без `npx`, `dlx` и загрузки runtime из сети.

Motion-фон рендерится покадрово отдельным этапом, поэтому создание эфирного Reels обычно занимает заметно больше времени, чем обычная подкаст-раскладка, и может идти дольше длительности самого фрагмента. Скорость зависит от длины клипа и производительности компьютера; актуальные стадии показывает карточка проекта. Кэш ускоряет повторный смысловой анализ визуального плана, но готовое motion-видео для каждого запуска всё равно рендерится заново.

Для отделения участников от демонстрации сервис семплирует кадры и определяет стабильные кластеры участников. При поиске основного спикера учитываются зелёная рамка Zoom, движение в области рта и размер лица; участник с наибольшим подтверждённым временем речи закрепляется в левом слоте, второй устойчиво найденный участник — в правом. Переключение «1/2 спикера» скрывает или показывает правый слот, не меняя идентичность и стороны участников.

Результат анализа раскладки сохраняется в `workspace/highlights/<project_id>/work/<clip_id>/vertical/broadcast_layout.json`. В отчёте указаны найденные участники, моменты переключений, геометрия speaker inset, безопасные области, confidence и причины fallback. Рядом сохраняются `visual_plan.json`, fingerprint запроса и журнал HyperFrames. Эти файлы полезны для диагностики записи, в которой автоматическая раскладка или визуальный план выбраны неточно.

Определение экрана и говорящего является локальной визуальной эвристикой, а не голосовой диаризацией. Качество зависит от раскладки Zoom, размера плиток участников, освещения, видимости лица и наличия зелёной рамки. Статичные аватары, очень мелкая галерея, нестандартное расположение демонстрации или частые переключения могут привести к задержке либо неверному выбору.

Motion-презентация опирается на произнесённый текст и заголовок выбранного момента; визуальный анализ экрана помогает отделить участников, но не распознаёт семантически каждую исходную вкладку или деталь слайда. Поэтому точная копия показанного экрана, мелкие подписи и элементы интерфейса не гарантируются. Перед публикацией эфирные ролики рекомендуется просмотреть.

## Что выполняется автоматически в режиме «Подкаст»

- определение монтажных склеек;
- поиск лица и центрирование актуального крупного плана;
- двухъярусная раскладка для общих планов с двумя участниками;
- центрирование каждого из двух спикеров в своей половине вертикального экрана с разделительной линией;
- локальная транскрипция с пословными таймкодами;
- одно слово субтитров за раз;
- экспорт 1080×1920, H.264/AAC, 30 fps;
- проверка разрешения и длительности результата.

## Как теперь собираются ролики

Ролик — монтаж из нескольких кусков эфира: хук, контекст, суть, пример, вывод. **Куски всегда идут в естественном (хронологическом) порядке записи.** Автоматического «выноса хука» из другого места в начало нет: он тянул чужие обрывки, швы не держались, а перестановка ломала предложения. Единственный допустимый разрыв между кусками — более поздний возврат спикера к ТОЙ ЖЕ мысли (продолжение). Открытие ролика чинится только так: отбросить ведущие предложения или расширить начало НАЗАД на предыдущие предложения записи (чтобы введён был герой/тема). Ответ ИИ, где куски перечислены не по порядку, при компоновке и критике приводится к порядку записи, а при ремонте отклоняется (`_natural_order`, `_raw_in_order`). Для визуала у каждого ролика есть `hook_text` — короткий (до 8 слов) заголовок-хук для титра на экране; он не озвучивается и в звук не вставляется; в интерфейсе и галерее он подписан «Хук для визуала». Шаги (`reel_factory/editorial.py`, `reel_factory/assembly.py`):

1. **Транскрипция.** Whisper с подсказкой `initial_prompt` («Ну, э-э, вот. Значит, м-м, как бы мы, мы…», для английского — аналог): он сохраняет пунктуацию и слова-паразиты вместо «причёсывания» речи. У каждого слова есть очищенный `text` (для субтитров) и исходный `raw` с пунктуацией (для границ предложений). Подсказка отключается опцией `keep_disfluencies: false`. `condition_on_previous_text` намеренно не выключается: иначе подсказка действует только на первое окно и стиль дрейфует к «чистому» тексту. Для русского рекомендуем модель «Точное» (`small`).
2. **Предложения.** Расшифровка режется на пронумерованные предложения S0001… по пунктуации, сегментам и паузам.
3. **Карта тем.** ИИ по всей записи находит темы, тезисы, тип темы (`kind`: list / story / thesis / advice / qa) и все места, где тема обсуждается (включая возвраты); для перечней — диапазоны каждого пункта (`items`).
4. **Компоновка и пропущенные моменты.** По умолчанию `max_clips=0` («все ролики»): темы карты идут пакетами, на каждую просится 0–2 ролика, отбора «топ-N» нет — ролик остаётся, если мысль в нём цельная. Опция `audience` (по умолчанию: «айтишники: джуны и мидлы, фронтенд/бэкенд, ищущие работу; боли — рынок, найм, HH, собеседования, зарплаты, накрутка опыта»; пустая строка отключает) передаётся в промпты компоновки, прохода пропущенных моментов и главного редактора как контекст «что интересно», а не как фильтр. Первая фраза — сильное утверждение/вопрос/цифра, не разминка. Принцип — одна мысль на ролик: у каждого есть `thesis` и `format` (list / thesis / story / advice / contrast). Кейс не склеивается с чужим тезисом, а становится отдельной `story`. Перечень (`list`) покрывает ВСЕ пункты по порядку. **Длинные сильные ролики не выбрасываются:** list и story могут идти до `max_duration × 1.6` (144 с при max 90), если критик оценил их сильными (`completeness` и `single_idea` ≥ 7); без сильной оценки потолок прежний (list ×1.4, story ×1.0); если ролик длиннее даже ×1.6 — он делится на два самостоятельных ролика (`_split_long`: ИИ предлагает деление, без ответа — деление пополам по границе предложения; части помечены `split_of`), а не отсеивается. **Проход «пропущенные сильные моменты»** (`_coverage_pass`, после компоновки, до критика, опция `coverage`): один запрос по ВСЕЙ расшифровке (на длинной записи — по частям), где уже покрытые предложения помечены «·»; ИИ ищет цитаты, реплики зала, на которые реагирует спикер («меня даже за еду сейчас работать не берут»), живые личные истории и кейсы, резкие утверждения с цифрами — и собирает вокруг них новые кандидаты в естественном порядке (`source: coverage`, `moment`); дальше они проходят критика и остальные стадии как обычные. Предпочтителен один непрерывный отрезок; далёкий кусок допускается, только если продолжает ту же мысль, не более 3 областей записи. Роли hook / context / point / example / payoff, последний — payoff; приветствия и «меня слышно?» исключаются.
5. **Критик (до 2 раундов) — отсев только за явные дефекты.** Оценивает ролик «глазами нового зрителя»: хук, законченность, ясность, самодостаточность и `single_idea`, плюс вердикт `ok|jump` на КАЖДЫЙ стык. Жёсткий отсев (`rejected`) — только: оценка completeness/clarity/standalone/single_idea ≤ 4 (в т.ч. нет вывода), нерешённый скачок между разными мыслями (стык `jump`, не снятый после ремонта), более 3 областей записи. Всё остальное — «почти прошёл» — идёт в ремонт. **Локальный дефект — подрезка, а не отсев.** Критик, ремонт, главный редактор и отсмотр видео могут вернуть `trims` — дословные фразы внутри предложения («в кавычках софты», паразитная фраза, повисшая половина предложения на стыке): код находит слова (`_locate_phrase`) и вырезает их при чистке (`forced_cuts`, причина `defect`, ролик остаётся, поле `local_fixes`); стык, у которого мешал только такой обрывок, после выреза считается `ok`. Решение главреда `drop` вместе с `trims` превращается в `publish` с вырезом.
6. **Кодовые правила и раунд 3 «ремонт».** Каждый кусок обязан начинаться с начала самостоятельного предложения: не с «и / а / но / плюс / также / то есть / поэтому…» и не с обрывка предложения, разрезанного паузой (строчная буква, а предыдущее предложение не закончено точкой) — тогда добавляется предыдущее предложение (до 3 раз; если оно — конец другого куска, куски склеиваются в нужном порядке), а если не вышло — обрывок снимается с начала куска или кусок из одного обрывка убирается (если ролик остаётся достаточно длинным); ведущее «и/а/но/вот/ну» снимает чистка. Служебные хвосты в конце («в чате правильно написали», «я про это пост писал», «как я говорил», вопрос залу) снимаются, если ролик и без них заканчивается законченным предложением. Затем «ремонт» (критик, раунд 3, задача `repair`): ИИ получает ролик, список всех проблем раундов 1–2, ±15 предложений вокруг и обязан вернуть исправленные куски с ответом по каждой проблеме (`addressed`) и новыми оценками.
7. **Главный редактор** (`chief_editor`, один запрос, opus, по ВСЕМ кандидатам и карте тем). По каждому кандидату — `publish | repair_more | drop` с причиной, итоговый ранг («выложил бы я это на наш канал?»), исправленное название, если оно не соответствует тексту, дубли одной истории (остаётся лучший). Покрытие: каждая тема с силой ≥ 70 и каждая тема `kind=list` должна быть представлена роликом, если для неё есть кандидат — в код встроена принудительная проверка (при необходимости из отсеянных критиком восстанавливается лучший кандидат темы). `repair_more` получает ещё один раунд ремонта и идёт в выпуск. Порядок выдачи — ранг главреда (`chief_editor.rank`). **Спин-офф:** из сильного длинного ролика главред может выделить самодостаточную часть (например, из «Идеальный кандидат невидим для HH» отдельно «HH пессимизирует резюме» с её кейсом) — оба ролика остаются в выпуске (`spinoff_of`, куски только из родительского ролика, в естественном порядке). Опция `chief_editor: false` отключает этап (тогда ранжирует критик).
8. **Отсеянные не удаляются.** Каждый отсеянный кандидат сохраняется как `rejected: {stage, reason, scores}` вместе с кусками и остаётся пригодным к рендеру. В интерфейсе они лежат в свёрнутом блоке «Не прошли проверку»; кнопка «Всё равно сделать» переносит кандидата в основной список и выбирает его для рендера.
9. **Чистка.** Вырезаются слова-паразиты, ложные старты, повторы и отступления (детерминированный минимум плюс предложения ИИ, не более ~20% слов куска). Отключается галочкой «Убирать слова-паразиты и паузы» (опция `tighten`). Для отсеянных — только детерминированный минимум. Итоговая длительность: нижняя граница жёсткая (0.85·min), верхняя допускает превышение до 20% (для сильных историй и перечней; в `critic.problems` остаётся пометка «длиннее целевого окна»).
10. **Сборка и рендер.** `assembly.keep_intervals` строит интервалы без вырезов, `assemble_clip` склеивает их ffmpeg в `horizontal.mp4`, `remap_transcript` переносит слова на новую шкалу — по ним делаются субтитры. Дальше работают прежние рендеры «Подкаст» и «Эфир». Длительность готового файла проверяется относительно собранного клипа (а не исходного диапазона). В конец ролика добавляется 0.3 с «воздуха» после последнего слова (`tail_pad`), иначе звук обрывается на слове. Эффект «наезда» камеры на стыках (jump-cut punch-in) пока не добавлен.

## Запуск на новом эфире: run_reels.py

Одна команда, без ручных шагов (рендер идёт строго по очереди):

```bash
PYTHONUTF8=1 HF_HOME="$PWD/.tools/hf" .venv/bin/python run_reels.py <video_path>   # Windows: .venv\Scripts\python.exe run_reels.py <video_path> \
    [--out DIR] [--provider claude|codex] [--model small|base] [--min 30 --max 90] [--audience "текст"] \
    [--no-review] [--no-coverage] [--parallel 3]
```

По умолчанию `--out` = `results/<имя-видео>/`, провайдер `claude`, модель распознавания `small` (точная), окно 30–90 с. Для экономии квоты можно задать `REEL_CLAUDE_MODEL=sonnet`.

Что происходит (весь код — в `reel_factory/batch.py`, это те же функции, что использует приложение):

1. **Транскрипция** (точная, пословная, со словарём IT-терминов) — кэш `<out>/transcript.json`.
2. **Смысловой монтаж, все ролики**: карта тем → компоновка → пропущенные сильные моменты → критик → ремонт → главный редактор (покрытие тем, дубли, спин-оффы) → чистка речи. Порядок кусков всегда естественный; локальные дефекты подрезаются, а не бракуются; длинные сильные ролики до ×1.6 или делятся на два.
3. **Рендер** каждого ролика (подкаст вертикальный `cNNN_vertical.mp4` + горизонтальный `cNNN_horizontal.mp4`, текст `cNNN_text.txt`, сырой звук) и каждого отсеянного кандидата, у которого есть куски (`rejected/rNNN_*`).
4. **Отсмотр готового видео** по содержанию и звуку (картинка не оценивается) с одной авто-правкой в естественном порядке.
5. **Отчёты**: `report.json` и галерея `index.html` — ролики с видео, названием, «Хук для визуала» (`hook_text`), тезисом, форматом, длительностью, рангом и причиной главреда, оценками критика, вердиктом/оценками/замечаниями отсмотра, сворачиваемым текстом; раздел «Не прошли проверку» — с видео, стадией, причиной и оценками.

Журнал с таймингами этапов — `<out>/run.log` (и `timings.json`). Возобновление: повторный запуск с тем же `--out` продолжает с места остановки (транскрипт, ответы ИИ в `_work/editorial/`, готовые ролики в `_state/` не пересчитываются). Чтобы пересобрать монтаж с другими настройками, удалите `<out>/candidates.json` и `_work/editorial/` (транскрипт можно оставить). Исследовательский скрипт «тест входа» лежит в `experiments/hook_test.py` и в поток не входит.


## Шеф-редактор по готовому видео

После рендера (опция `video_review`, по умолчанию включена; галочка «Шеф-редактор отсматривает готовые ролики» рядом с кнопкой «Сделать вертикальные») `reel_factory/review.py` ОТСМАТРИВАЕТ готовый вертикальный mp4 — так, как это делает человек, а не по тексту монтажа:

1. **Только звук и речь.** Картинку шеф-редактор НЕ оценивает (кадры и контактные листы строятся лишь при `review_visual: true`, по умолчанию выключено). Вход: перераспознанный звук готового ролика с таймкодами, моменты склеек, автонаходки по звуку, название и тезис, допустимое окно длительности.
2. **Звук.** Звук ГОТОВОГО ролика заново распознаётся faster-whisper (пословно) и сравнивается с ожидаемым текстом монтажа: срезанные слова рядом со стыками, задвоенные слова, паузы > 0.6 с, обрыв в конце, скачки речевого уровня на стыках (p80 громкости окон 0.6 с слева/справа, порог 10 дБ).
3. **ИИ-отсмотр.** Один запрос на ролик (`video_review`, effort high). Оценки 0–10: `hook`, `idea_disclosure`, `flow`, `audio` (+ `visual` при `review_visual`). Вердикт считается по оценкам: `reject` — любая ≤ 3; иначе `needs_edit` — любая < 6; иначе `publish`. Есть `issues` с таймкодами, `suggested_fix` (операции над кусками) и подпись для поста.
4. **Авто-правка — не больше одной на ролик.** Если вердикт `needs_edit` и правка выражается кусками, кандидат пересобирается (правка обязана уложиться в окно длительности: сверх окна режутся context/example, hook/payoff не трогаются, иначе правка отклоняется), ролик рендерится заново и отсматривается ещё раз; исправленная версия заменяет исходную, только если она не хуже. Отключается `video_review_autofix: false`. Правка работает только в естественном порядке (`extend_*` расширяют кусок назад/вперёд по записи, перестановок нет), умеет вырезать фразу (`cut_phrase`: локальный дефект — подрезка, а не «не публиковать») и всегда перепроверяет длительность.

**Длительность и рваность (монтаж).** Итоговое окно: 0.85×min … max (+5% допуска; для сильных list/story — до 1.6×max, см. шаг 4); после каждой стадии, меняющей куски (критик, ремонт, repair главреда, авто-правка), длительность проверяется заново: сначала режутся context/example, hook/payoff — никогда, если уложиться нельзя — ролик отсеивается с причиной (`stage: duration`). Начало ролика — целые предложения (не короче 4 слов), без повторов слов в первые 10 с и на стыках кусков; чистка не оставляет между вырезами фрагменты короче 0.6 с, режет не больше 2 раз на предложение (одиночные слова-паразиты не считаются) и не сводит одинаковое слово встык.

**Звук при сборке.** По умолчанию (`audio_mode: "raw"`, во всех путях: приложение, `run_reels.py`) звук идёт «как записан»: без выравнивания громкости (gain), без `loudnorm`/`dynaudnorm`, только короткие fade ~15 мс на склейках. Остаются правила склейки v4: границы кусков подрезаются по реальной громкости и режутся в самой тихой части паузы, пауза сжимается только если она ≥ 0.9 с, бюджет склеек (не чаще одной на ~4 с). Режим `audio_mode: "leveled"` (скрытая опция) возвращает выравнивание уровней кусков (до ±9 дБ) и `loudnorm=I=-16:TP=-1.5:LRA=11`. Подрезка краёв по звуку отключается `audio_polish: false`.

Словарь терминов (`asr_glossary`, по умолчанию IT-лексика для русского) добавляется к подсказке Whisper (поле «Словарь терминов» в настройках; пустое поле отключает).

Настройки: «Сколько роликов собрать» (0–20; по умолчанию 0 = без ограничения), «Аудитория эфира» (подсказка редактору, не фильтр), минимум/максимум секунд (по умолчанию 30/90, максимум до 180). Старые проекты без `segments` по-прежнему открываются и рендерятся как один кусок без вырезов. Явно выбранный «Встроенный анализ» даёт окна без смыслового монтажа.

**Отладочные файлы** лежат в `workspace/highlights/<проект>/work/editorial/`: `editorial_result.json` (`{"clips": итог, "dropped": [{title, stage, reason, scores}]}` — почему каждый кандидат отсеян), `editorial_sentences.json`, `editorial_topics.json`, `editorial_critique_raw_2.json` (второй раунд критика), `editorial_compose_raw.json`, `editorial_after_critique.json`, `editorial_tighten_raw.json`, а также `topic_map*`, `compose*`, `critique*`, `tighten*` `.json`/`.log` — промпты и сырые ответы ИИ каждого шага. Для каждого отрендеренного ролика в `work/<c001>/` лежат `assembly.json` (интервалы склейки), `horizontal.mp4` и `transcript.json`.

## Где хранятся файлы

Исходники и результаты пакетных заданий сохраняются в `workspace/jobs/`, а проекты умной нарезки — в `workspace/highlights/`. При выборе Claude или Codex текст транскрипции передаётся выбранному CLI для смыслового анализа. Встроенный режим не отправляет транскрипцию ИИ-провайдеру.

## Режимы распознавания

- **Стандартное** (`base`) — рекомендуется для большинства чистых студийных записей.
- **Точное** (`small`) — лучше распознаёт сложные фразы, но требует заметно больше оперативной памяти.

Автоматическое распознавание иногда ошибается в именах, брендах и редких терминах. Для публикации важных роликов рекомендуется выборочно проверить текст.

## Распознавание через Deepgram

Облачное распознавание (модель `nova-3`, пословные таймкоды, пунктуация, слова-паразиты) работает на порядок быстрее локального Whisper и выдаёт транскрипт в том же формате (`words` с `text`/`raw`/`start`/`end`/`probability`, `segments`, `text`).

- **Ключ.** Берётся из переменной окружения `DEEPGRAM_API_KEY`, иначе из файла `.env` в корне проекта (строка `DEEPGRAM_API_KEY=...`), иначе из `.secrets/deepgram.env` (строка `DEEPGRAM_API_KEY=...`, права 600, папка в `.gitignore`). Ключ не пишется в логи, отчёты и сообщения об ошибках.
- **Опция `asr_provider`:** `auto` (по умолчанию: Deepgram, если ключ найден, иначе локально), `deepgram` (при сбое — понятная ошибка), `local` (faster-whisper). В `auto` при сбое Deepgram включается локальное распознавание, предупреждение попадает в `run.log` и `transcript.json` (`transcription.asr_warning`).
- **CLI:** `run_reels.py --asr deepgram|local|auto`. В веб-интерфейсе — выпадающий список «Распознавание речи».
- **Что отправляется:** аудио (моно, 16 кГц, mp3 48 кбит/с) и до 50 терминов из `asr_glossary` как `keyterm`. Сырой ответ кэшируется в `<work>/transcription/deepgram_response.json`, повторный запуск не тратит деньги.
